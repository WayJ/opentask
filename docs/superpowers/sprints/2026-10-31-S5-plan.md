# S5 — 状态映射配置化 + 鉴权接入 + 能力检查端点

本文件即 sprint 台账。一个 sprint = 一个 worktree/分支（`sprint/E2-S5`，基于 sprint/E2-S4 tip 7db78a6——本 sprint 直接扩展 S4 交付的契约模块，S4 落地后按 sync-then-FF 收敛）。同一时刻本载体仅一个 worker（用户裁定的 sprint 级并行模型，2026-10-31）。

## Decisions (D-x)

| id | decision | rationale | rejected alternatives |
|---|---|---|---|
| D1 | 分支基点为 sprint/E2-S4 tip 而非 main | S5 的全部工作（状态映射配置化、鉴权、capabilities）都在 S4 的 api/tasks/ 模块之上；基于 main 则模块不存在 | 基于 main —— 拒绝：无对象可扩展 |
| D2 | 鉴权按 D9 复用 access_token：API Key（Bearer）与 Orca 侧 OAuth2 client credentials 两模式 | epic Deliverable 既定；token 体系现成（models/access_token） | 新造鉴权 —— 拒绝：D9 否决 |
| D3 | 状态映射配置放 config/*.yaml（contract.status_mapping 段）+ 代码默认表兜底 | epic DoD 6「可配置 + 未配置用默认表」；yaml 已是配置中心（S2 刚切 PG 段） | 环境变量/DB 表 —— 拒绝：映射是结构化数据，yaml 合适 |
| D4 | 并行模型调整记录：一载体一 worker（2026-10-31 用户裁定「sprint 级 worktree 并行」） | 多 worker 共享一个 worktree 有 git index/测试互扰风险；并行度改由多 sprint 各自载体承担 | 单 worktree 多 worker 互斥路径 —— 拒绝：用户明令调整 |

## Stories & Tasks

### Wave 1 — 映射配置化

- [ ] `backend/config/*.yaml` 增 `contract.status_mapping` 段（Orca 状态 ↔ IssueStatus 双向表），代码默认表兜底（未配置时）
- [ ] api/tasks/ 映射层读配置；往返正确性用例（Orca → OpenTask → Orca）

### Wave 2 — 鉴权 + capabilities

- [ ] 契约层鉴权依赖：access_token 校验（Bearer API Key 模式）；OAuth2 client credentials 模式（token 交换）
- [ ] 401 独立语义（区别于 403/503，错误体可辨识——为 S6 错误语义铺路）
- [ ] `GET /capabilities`：端点支持情况 + 契约版本
- [ ] tests/tasks/ 扩展：映射配置化用例、鉴权 401 用例、capabilities 用例
- [ ] `backend/README.md` 契约层鉴权配置说明（与 yaml 同提交——doc_sync_map）

## Definition of Done

- [ ] Orca 用「自定义任务源」注册 OpenTask 后，OpenTask 的 issue 能在 Orca 侧正常列出、读取、创建、更新、状态流转
- [ ] `GET /tasks` 支持 `updated_since` 增量游标，重复拉取同一游标不返回重复数据
- [ ] `POST /tasks` 创建的 issue 回传到 OpenTask 后，字段（title/description/assignee/status/labels）完整落库
- [ ] `PATCH /tasks/{id}` 更新状态后，OpenTask 内部 issue 状态同步变更，并写入既有 timeline 记录
- [ ] `DELETE /tasks/{id}` 采用软删除（OpenTask 现有 `is_deleted` 语义），不物理删除数据
- [ ] 状态映射可通过配置调整，未配置时使用默认映射表且能正确往返（Orca → OpenTask → Orca）
- [ ] 契约 OpenAPI spec 已生成并随代码发布，字段与实现一致
- [ ] 端点不可达、鉴权失败、schema 违规三类错误有独立的错误码与可读消息
- [ ] 该 API 层有单元测试覆盖 CRUD 全路径与增量游标边界
